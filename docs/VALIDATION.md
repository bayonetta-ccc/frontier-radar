# 验证方案

> 这份文档把“看起来不错”变成可执行、可复核的验证流程。
> 目标不是证明产品成功，而是尽快发现它在什么条件下会失败。

## 0. 验证问题

按优先级：

1. **用户是否愿意让系统长期保存并更新自己的关注清单和关键判断？**
2. 系统是否让用户发现了原本会漏掉的重要变化？
3. “与我何干”是否具体到能改变一个动作或判断？
4. 无实质变化时明确不推送，用户是否反而更信任它？
5. 判断更新是否可审计、可纠错、可回滚？

如果 1 是否定的，其他指标再好也只是“临时搜索工具”。

## 1. 被试与场景

- **一类用户 × 一个决策**，不要同时验证多个领域。
- 推荐场景：固态电池 × 产业研究员 × 6 个月内形成路线建议。
- 连续运行 **3—4 期**（建议每周一期），每期真实采集或人工补录信号。
- 招募 2—3 名同角色用户做交叉复核，避免只验证“作者自己的判断”。

## 2. 运行方式

```bash
# 第 1 期：建立基线，用户确认/修改/删除判断
python -m frontier_radar task new --demo
python -m frontier_radar run --mode baseline --now 2026-08-01T09:00:00+08:00

# 第 2—4 期：更新
python -m frontier_radar run --now 2026-08-08T09:00:00+08:00
python -m frontier_radar run --now 2026-08-15T09:00:00+08:00
python -m frontier_radar run --now 2026-08-22T09:00:00+08:00

# 每期结束后
python -m frontier_radar metrics --json > data/metrics-$(date +%F).json
```

真实使用时把 `--source offline` 换成 `--source live`，并在 `ingest` 中记录来源可达性。
如果某期没有新来源，**允许不运行**；这也是一种数据。

## 3. 抽样复核表

每期随机抽取 5 条进入判断的信号 + 5 条被拦截的信号，由复核人独立填写：

| 字段 | 说明 |
|---|---|
| 信号标题 / 链接 | 原文是否可访问 |
| 系统类别 | 论文/专利/中试/客户验证/量产计划… 是否准确 |
| 系统信息层 | 事实/口径/推断/观点/传闻 是否准确 |
| 系统阶段 | 是否越级（例如把“计划”读成“已量产”） |
| 变化类型 | 新增/增强/削弱/证伪/转向 是否正确 |
| 证据是否支持结论 | 支持 / 部分支持 / 不支持 |
| “与我何干”是否具体 | 1—5 分 |
| 是否应推送 | 是 / 否 / 不确定 |

被拦截的 5 条还要额外回答：**拦截理由是否成立？**
这一步是检查“去噪能力”是否以漏掉重要信息为代价。

## 4. 指标与质量门

`python -m frontier_radar metrics` 输出：

| 维度 | 指标 | 建议门槛 | 失败意味着什么 |
|---|---|---|---|
| 信息质量 | 重复率 | ≤ 15% | 去重规则不足，用户在读同一篇稿子 |
| 信息质量 | 噪声率 | ≤ 35% | 营销/观点/传闻未被拦截 |
| 信息质量 | 变化卡链接完整率 | = 100% | 结论无法回溯 |
| 信息质量 | 变化卡摘录完整率 | = 100% | 用户只能相信摘要 |
| 更新质量 | 变更理由覆盖率 | = 100% | 不可审计的修改 |
| 更新质量 | 单期置信度移动幅度 | 增强 ≤ +0.12 / 削弱 ≤ −0.18 | 一期证据把判断推成“确定事实” |
| 更新质量 | 证伪是否有人工确认 | 是 | 高风险结论被自动改写 |
| 用户价值 | 有变化期数 / 总期数 | 观察值，不设门槛 | 全是静默说明主题选错了 |
| 用户价值 | 用户查看原始证据比例 | 越高越好 | 报告没有说服力 |
| 长期留存 | 连续维护关注主题的周数 | ≥ 3 周 | 仍是一次性工具 |

**注意**：待确认数量不为 0 不是失败，它说明系统没有绕过人工复核。
质量门通过也不代表产品成立，只说明“过程没有明显崩坏”。

## 5. 用户访谈提纲

每期结束后 15 分钟：

1. 这一期里，哪一条是你原本不会注意到的？
2. 有没有哪条结论你不同意？你依据什么？
3. “与我何干”那段，你会因此改变一个动作吗？如果没有，缺什么？
4. 如果系统这周什么都没推送，你会觉得它坏了，还是觉得它可靠？
5. 你愿意把哪些判断交给它长期跟踪？哪些绝不？
6. 如果下周停用，你会怀念哪一部分？

第 5、6 题直接对应“个人情报资产”假设。

## 6. 反例与停止条件

出现以下情况时，先停下来修机制，而不是加功能：

- 连续两期出现“把企业口径当作独立验证”；
- 证伪被单一营销稿触发；
- 用户需要花比手动搜索更长时间核对报告；
- 静默期被用户理解为“系统失效”；
- 判断基线与用户真实决策无关（说明任务输入设计失败）。

## 7. 结果如何进入产品

- 复核表中的错误分类进入测试用例（`tests/`）；
- 反复出现的噪声模式进入 profile 的 `noise` / `lexicon`；
- 阶段误判进入 `stage_patterns` 或 `CATEGORY_STAGE_CAP`；
- 用户纠错进入 `feedback` 表，并在下一期报告中作为复核线索；
- 任何涉及“自动改判断”的改动，都必须同时更新质量门与审批规则。
