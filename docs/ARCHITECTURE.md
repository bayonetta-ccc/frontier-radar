# 架构说明

## 1. 设计目标

1. **可复现**：同一个 fixture、同一组参数，任何机器上都得到同一份判断更新。
2. **可审计**：每条结论都能回答“依据哪条信号、哪次运行、哪个版本、为什么改”。
3. **可回滚**：判断修改是版本化事件，不是覆盖写入。
4. **可扩展**：新增领域只加一个 JSON profile，不改核心代码。
5. **零依赖**：Python 标准库 + SQLite；LLM、向量库、爬虫框架都不是必需项。

## 2. 分层

```text
┌──────────────────────────────────────────────────────────────┐
│ 接口层   cli.py（命令行） / web.py（本地 HTTP） / engine.py（静态站点） │
├──────────────────────────────────────────────────────────────┤
│ 报告层   render.py（Markdown/HTML） · pipeline.py（组装 Digest）  │
├──────────────────────────────────────────────────────────────┤
│ 判断层   claims.py（证据门槛、变化类型、版本、审批、回滚）            │
├──────────────────────────────────────────────────────────────┤
│ 证据层   evidence.py（分类、阶段、信息层、实体、锚点、证据强度）       │
├──────────────────────────────────────────────────────────────┤
│ 采集层   sources.py（fixture / RSS / Atom / HTML）                │
├──────────────────────────────────────────────────────────────┤
│ 存储层   db.py（SQLite） · models.py（数据结构） · text.py（工具）    │
└──────────────────────────────────────────────────────────────┘
        profile.py + config/domains/*.json（领域知识，数据而非代码）
```

依赖方向自上而下，不允许反向：`claims.py` 不 import `cli.py`，`evidence.py` 不知道数据库。

## 3. 一次运行的时序

```text
run(task_id, now)
 ├─ 读取任务、上一次运行、来源开关
 ├─ 采集：collector_for(mode).fetch(sources)
 ├─ 时间窗过滤（published_at ∈ [period_start, period_end]）
 ├─ 去重：URL 规范键 / 正文哈希 / 标题相似度（历史 + 本批次）
 ├─ 分类：类别 → 阶段 → 信息层 → 实体 → 锚点 → 新颖性 → 噪声
 ├─ 落库：signals（保留噪声与重复，便于审计）
 ├─ baseline：建立 3—5 个判断（全部 needs_review）
 │  update：engine.evaluate() 逐条判断
 │    ├─ 支持/相反证据 → 独立来源组
 │    ├─ 门槛判定 → new/strengthen/weaken/falsify/shift/no_change
 │    ├─ 高风险或来源不足 → pending（写入待确认版本，不改当前判断）
 │    └─ 普通修改 → applied（写版本 + 更新证据台账）
 ├─ 组装 Digest：摘要、变化、时间线、未推送、覆盖、相关性、指标
 ├─ 导出 digest.json / digest.md（含 signal_index，支持离线重放渲染）
 ├─ 发布静态站点 data/web/
 └─ 记录 run、事件、状态
```

## 4. 数据模型

```text
tasks ──< sources
  │
  └──< runs ──< signals ──< evidence >── claims ──< claim_versions
                │                        │
                └──< artifacts           └──< feedback / events
```

- `signals` 以 `(run_id, signal_id)` 为主键，保留噪声与重复记录（不参与判断），
  这样“为什么这条没被推送”也可审计。
- `evidence` 是判断与信号的多对多关系，带 `direction`（support/contra）与 `weight`。
  证伪发生后，旧的支持证据会从“当前依据”移除，但版本历史里仍保留触发记录。
- `claim_versions` 是判断的唯一真实来源：`claims` 表只是最新版本的物化视图，
  回滚 = 以目标版本内容生成一个新版本，中间版本不删除。
- `feedback` 记录用户对信息价值与判断错误的反馈，进入 `metrics` 与后续复核。

## 5. 证据强度与门槛

```text
evidence_strength = 信息层强度(0.16—0.92)
                  × 来源权威(0.35—0.9)
                  × 类别权重(0.15—1.0)
                  × 阶段具体性(0.75—1.0)
```

聚合采用递减收益（第 n 条乘以 `0.68^n`），避免同稿多投把权重堆满。

判断更新：

```text
新增支持/反向证据 → 只统计本期（历史证据不重复计分）
new_support_weight = Σ 支持权重（递减）
new_contra_weight  = Σ 相反权重（递减）
独立来源组 = 本期证据来源的 independent_group 去重数

projected = clamp(confidence + 0.62×支持 − 0.55×相反 + 0.35×历史支持底盘, 0.08, 0.88)
单期移动上限：增强 ≤ +0.12，削弱 ≤ −0.18

falsify   : 相反权重 ≥ 0.55 且（独立组 ≥ 2 或出现当事方明确澄清）→ pending（必须人工确认）
shift     : 阶段跃迁 ≥ 2（技术/路线/标准类），或相反证据指向更低阶段
weaken    : projected − confidence ≤ −0.10
strengthen: projected − confidence ≥ +0.12 且（有历史支持 或 独立组 ≥ 2）
new       : 首次出现新证据但独立来源不足 → unresolved（不升级）
no_change : 其余有信号但未达门槛的情况
```

## 6. 阶段模型

阶段是**领域相关的**，由 profile 的 `stages` 定义，默认刻度：

```text
S0 论文/预印本 → S1 实验室样品 → S2 中试线 → S3 客户验证 → S4 量产计划 → S5 实际量产
```

规则：

- 类别有阶段上限（例如“标准”类最高 S4），防止发布会/招聘被读成量产；
- 负向信号（延期/失败）不能由“投产/量产”等词抬高阶段，最高记 S2；
- 标准类判断可以借用同一刻度表达“草案 → 征求意见 → 发布实施”，但不会触发技术路线跃迁；
- 阶段推进 ≥ 2 级才改写判断（`shift`），微调只影响置信度。

## 7. 人工确认闸门

以下情况不自动写入当前判断，而是生成一个 `user_correction='pending'` 的待确认版本：

- 证伪（始终）；
- 高风险判断（anchor 的 `high_risk: true`，例如量产时间表、监管结论）；
- 置信度低于任务阈值时的增强；
- 独立来源组不足 2 个的修改。

已有待确认修改时，新证据不会再叠加版本；报告会把这条判断标为“未解决”，
并提示先处理待确认修改。这是为了防止“用连续多期的小更新绕过一次人工复核”。

## 8. 渲染与导出

- `digest.md`：可归档、可贴进周报的完整文本；
- `digest.json`：结构化报告 + `signal_index`（渲染所需的最小信号集），可离线重放；
- `data/web/`：静态站点（总览、判断库、每期报告、说明页），无外部资源依赖；
- `web.py`：本地服务，读同一批产物，增加 POST 接口（反馈、确认、驳回、回滚、停用）。

HTML 全部由服务端转义渲染，不拼接未经转义的用户输入；POST 有同源校验、体积上限与重定向白名单。

## 9. 可扩展点

| 想扩展 | 改哪里 |
|---|---|
| 新领域 | 新增 `config/domains/<slug>.json` + `config/fixtures/<slug>/signals/*.json` |
| 新来源类型 | `sources.py` 增加 Collector 或 `SourceDef.kind` 的处理 |
| 新证据规则 | `evidence.py` 的类别/阶段/信息层词表或 `claims.py` 的 Thresholds |
| 新报告视图 | `render.py` 增加渲染函数，`pipeline.py` 增加汇总字段 |
| LLM 起草 | 在 `claims.py` 之外新增 `llm.py`，输出只作为 `needs_review` 的草稿 |
| 其他存储 | 实现 `db.py` 的接口子集，或替换 `Database` 类 |

## 10. 已知限制

- 规则分类对领域词表敏感，换领域必须重新标注 `category_blueprint` 与 `stage_patterns`；
- 标题相似度去重对“同一事件不同角度报道”偏保守（宁可漏合，不可错合）；
- `live` 采集只处理公开 RSS/Atom 与简单 HTML，不处理登录、反爬与付费墙；
- SQLite 适合单用户本地使用，不适合并发写入；
- 报告中的“与我何干”是模板化生成；接入 LLM 后可以更自然，但必须保留证据绑定与人工确认。
